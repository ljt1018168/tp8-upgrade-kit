# ThinkPHP 5.1 → 8.x 升级参考手册

> **定位**：基于一个真实业务系统（PHP 7.4.33 + TP5.1.41 → PHP 8.4.27 + TP8.1.2）完整实战，  
> 提炼出的可复用方法论。**不是原项目的过程记录**，  
> 而是给「下一个要升级的项目」的对照手册。

| 项    | 内容                                                        |
| ---- | --------------------------------------------------------- |
| 适用场景 | TP5.1（含 TP5.0）单体/多应用项目升级到 TP8；PHP 7.4 升级到 8.x             |
| 案例规模 | 4,021 个文件、252 个控制器、222 个模板、243 个类、约 120 张表                |
| 案例耗时 | 2 天（含 4 轮全站回归 + 上线前门禁）                                    |
| 案例结果 | 冒烟 14/14；全站 373 条可执行入口 95.4% 通过；500 从 35 降至 3（且均定性为非代码缺陷） |
| 使用方式 | 第一章判断「要不要升」→ 第三章照路线走 → 第五章遇坑查表 → 第六/七章做门禁 → 附录勾清单         |

## 一、升级背景与目标

### 1.1 案例背景（输入条件，用于对照你的项目）

| 维度     | 本案例情况                                                                 | 对升级难度的影响                             |
| ------ | --------------------------------------------------------------------- | ------------------------------------ |
| 框架版本   | TP 5.1.41 LTS（长期未升级）                                                  | 跨 6 个大版本，断层最多                        |
| PHP 版本 | 7.4.33（已 EOL）                                                         | 需同时跨 8.0/8.1/8.2/8.3/8.4 五个小版本的破坏性变更 |
| 代码量    | 252 控制器 / 222 模板 / 4,021 文件                                           | 人工逐文件改不可行，必须脚本化 + 兼容层                |
| 依赖深度   | 深度使用 `success/error`（1,063 处）、`config()` 裸键、`select()` 结果直接 `array_*` | 兼容层必须覆盖到「基础设施级」，不能只改调用点              |
| 业务关键性  | 企业管理系统，CAS 单点登录 + 财务数据 + 批量导出                                        | 不能停机、不能"试错上线"，必须灰度                   |
| 测试资产   | **0 单测、0 CI**                                                         | 最大风险项：所有回归靠人工 → 必须先造回归工具             |
| 改造约束   | 原项目必须保持可运行                                                            | 决定「复制副本」而非原地改                        |

> **关键判断**：「0 测试资产」是这类老项目最普遍、也最致命的前提。  
> 它直接决定了升级的第一步不是改代码，而是**先建立可量化的验证手段**（见 7.3）。

### 1.2 目标定义：什么叫"升级完成"

不要用「编译通过 / 首页能打开」当完成标准。本案例定义的可验收目标（建议直接沿用）：

| 层级      | 验收标准                                                      | 是否可量化           |
| ------- | --------------------------------------------------------- | --------------- |
| L1 能启动  | 框架初始化、路由解析、类加载无 Fatal                                     | ✅ `0 错误`        |
| L2 能连库  | DB / Redis / Session / Cache / 模板 / Excel / Validate 全链路通 | ✅ 冒烟 14 项全 PASS |
| L3 能登录  | CAS 完整走通，会话能跨请求保持                                         | ✅ 真实会话可复用       |
| L4 能跑业务 | **所有可安全执行的入口**返回 200 或「已定性非缺陷」的错误                         | ✅ 通过率 ≥ 95%     |
| L5 能上线  | 环境配置、安全暴露面、回滚路径全部闭环                                       | ✅ 门禁清单全绿        |

### 1.3 是否该升：五个必答问题

升级前必须能回答，否则不要开工：

| # | 问题                               | 不通过的信号                               |
| - | -------------------------------- | ------------------------------------ |
| 1 | PHP 7.4 EOL 后是否有强制合规要求（等保、审计）？   | 没有 → 可以先只升 PHP 8.2（LTS），框架不动         |
| 2 | 有无 0 测试资产？                       | 有 → 必须先补回归工具，工期 +30%                 |
| 3 | 是否深度依赖 TP5.1 的「隐式容错」（不判空、不初始化）？  | 是 → PHP 8 会把 NOTICE 升 WARNING，需专门降级层 |
| 4 | 是否有「控制器互调」「把 select 结果丢缓存」这类反模式？ | 是 → 必须做静态扫描，否则要等运行期才炸                |
| 5 | 能否拿到独立的预发环境 + 灰度能力？              | 不能 → 不要升，先解决发布能力                     |

### 1.4 本案例的结果基线（给你的项目做参照）

| 指标               | 升级前 | 升级后                                         |
| ---------------- | --- | ------------------------------------------- |
| 语法错误             | —   | 0（`app` / `config` / `route` / `vendor` 全扫） |
| 类加载              | —   | 243/243 成功                                  |
| 冒烟测试             | —   | 14/14 PASS                                  |
| 全站可执行入口          | —   | 373 条，356 通过（**95.4%**）                     |
| 500 错误           | 35  | **3**（缺参数 / 缺表 / 需签名，均非代码缺陷）                |
| PHP 8.4 与 8.3 差异 | —   | 逐 URL 比对仅 3 条不一致，无 8.4 特有问题                 |

## 二、涉及的模块与改动范围

### 2.1 改动分层模型（建议按此分层排期）

| 层           | 内容                      | 改动性质        | 本案例量级                                                                                          |
| ----------- | ----------------------- | ----------- | ---------------------------------------------------------------------------------------------- |
| **L0 运行环境** | PHP 版本、扩展、FPM 池、nginx   | 配置          | 18 个扩展自检；新建 8.4 FPM 池与原 7.4 池并存                                                                |
| **L1 依赖**   | `composer.json`、vendor  | 换代          | 10 个包升级 / 3 个移除                                                                                |
| **L2 配置体系** | `config/*`、`.env`、多环境目录 | **结构重写**    | `app/database/cache/session/view/log/middleware/console/route` 9 个 + 新增 `view.php`/`route.php` |
| **L3 兼容层**  | 重建 TP5.1 被移除的基础设施       | **新增代码**    | 7 个新增文件 + 2 个中间件/服务                                                                            |
| **L4 业务代码** | 控制器 / 模型 / 服务 / 模板      | 机械替换 + 定点修改 | 见 2.2 明细                                                                                       |
| **L5 部署**   | 目录结构、运行时目录、web 根        | 迁移          | `application/` → `app/`；`runtime` 清理；日志目录迁出 web 根                                              |

> **排期铁律**：L0~L3 完成前不要动 L4。  
> 本案例首轮就在「配置分组还没修好」时批量改业务代码，结果所有改动都无法验证，等于白改一轮。

### 2.2 本案例的改动清单与量级（作为你估算的锚点）

| #  | 改造项                                            | 数量      | 文件数    | 自动化程度              |
| -- | ---------------------------------------------- | ------- | ------ | ------------------ |
| 1  | `use think\Db` → `use think\facade\Db`         | 81      | 81     | 脚本全自动              |
| 2  | `Request::module()` → `app('http')->getName()` | 63      | 20     | 脚本全自动              |
| 3  | **`config('裸键')` → `config('app.裸键')`**        | **35**  | **18** | 半自动（需人工核对分组名）      |
| 4  | 模板内 `{:config('裸键')}` → 分组键                    | 5       | 3      | 人工                 |
| 5  | **`select()` 结果补 `->toArray()`**               | **121** | **21** | 脚本全自动（行内精确插入）      |
| 6  | 控制器互调补 `app()`                                 | 18      | 15     | 脚本扫描 + 人工修         |
| 7  | 命名空间常量重复定义改名                                   | 10      | 4      | 人工（PHP 8 起是 Fatal） |
| 8  | 隐式可空参数修正                                       | 2       | 2      | 人工                 |
| 9  | `Response` 子类签名 / Monolog Handler 签名           | 2       | 2      | 人工                 |
| 10 | `{$Think.session.x}` → `{:session('x')}`       | 1       | 1      | 人工                 |
| 11 | 相对路径 `require_once` → `__DIR__`                | 1       | 1      | 人工                 |
| 12 | `Cache::rm()` → `delete()`                     | 5       | 4      | 人工（grep 全扫）        |
| 13 | 兼容层新增文件                                        | —       | 9      | 参照 TP5.1 源码重建      |

**总特征**：约 330 处机械改动靠脚本完成，只有 <30 处需要人判断。  
**结论：升级的工程量不在"改"，而在"找到要改哪里 + 证明改对了"。**

### 2.3 估算你的项目量级（采样法，30 分钟）

```bash
# 采样 20 个控制器，统计 TP5.1 特有 API 密度
grep -rl "think\\\\Db;" app/ | wc -l                    # Db 门面
grep -rn "Request::module()\|request()->module()" app/ | wc -l
grep -rn "config('[a-z_]*')" app/ | wc -l              # 裸键（TP8 必失效）
grep -rn -- "->select()" app/ | wc -l                  # Collection 风险面
grep -rn "new [A-Z][A-Za-z]*(" app/ | wc -l            # 控制器互调风险面
grep -rn "\$this->success(\|\$this->error(" app/ | wc -l
```

经验公式（本案例校准）：

```
改造工时(人日) ≈ (Db门面文件数 × 0.05) + (裸键处数 × 0.02)
               + (select处数 × 0.01) + 兼容层固定 2 人日
               + 全站回归工具 1.5 人日 + 回归修复 2 人日
```

### 2.4 不需要动的地方（负面清单，防止过度改造）

本案例评估阶段列了 5 个「必须改」的项，实测 **全部不成立**：

| 评估结论                        | 实测                          | 教训               |
| --------------------------- | --------------------------- | ---------------- |
| `think\db\Where` 需改造（20 文件） | think-orm 4.0.50 内置，**零改动** | 先查新版源码，别信旧文章     |
| `topthink/think-image` 需安装  | 业务零引用，**直接移除**              | 依赖清单 ≠ 使用清单      |
| `action()` 助手需处理            | 真实调用 **0 处**                | 同上               |
| `${var}` 插值弃用需改             | 来自 TP5.1 框架内部，TP8 已消除       | 弃用警告先看 `file` 归属 |
| ~~`endroid/qr-code` 需升级~~ | **反面案例，见 2.4.1**：实际有引用，误判"零引用"后移除，导致推广二维码功能中断 | 不要照抄此结论 |

> **通用做法**：任何「必须改 / 可以删」的结论，先用 `grep` 验证**真实引用数**。
> 本案例 5 个「必须改」项里有 4 个是零引用 —— 零引用的依赖直接删除，比兼容便宜一个量级。
> **但"零引用"这个判断本身也可能错**，见下节。

### 2.4.1 反面案例：「零引用」误判导致功能中断

本案例把 `endroid/qr-code` 判为零引用并移除，上线前被用户点出来：

```
Class "Endroid\QrCode\QrCode" not found   ← 推广二维码功能
```

| 环节 | 实际情况 |
|---|---|
| 当时的搜法 | 按 composer 包名小写搜 `app/`：`grep -rn "endroid" app/` |
| 代码实际写法 | `use Endroid\QrCode\QrCode;` —— **首字母大写** |
| 结果 | 大小写不匹配 → 0 命中 → 判定"零引用" → 移除 |
| 真实引用 | 1 个文件（`QcodeService.php`）、2 个调用点 |
| 后果 | 功能中断，且**自动回归测不出来**（见 5.3 的 `WARN_EMPTY` 陷阱） |

**修正后的核查规范**（三条都要做）：

```bash
# 1) 大小写不敏感，且同时搜「包名」和「命名空间」
grep -rni "endroid" app/                        # 包名，忽略大小写
grep -rnF 'Endroid\QrCode' app/                 # 命名空间形态（-F 免转义）
grep -rn  "QrCode" app/                         # 短类名（抓 new 与静态调用）
# 2) 换工具交叉验证（同一条 grep 可能因 shell/alias 偶发漏搜）
#    用 ripgrep / IDE 全局搜索 / PHP 反射扫 use 语句，任选其二
# 3) 搜调用点而不只是 use 语句：看类名短名是否被 new
grep -rn "QrCode\|QrcodeService" app/
```

> **不要相信单次 grep 的"零命中"**。本案例在排查阶段亲历过同一条 `grep -rn "Endroid" app/`
> 先返回 0 行、再执行返回 4 行的现象（shell 层面偶发）。凡是要据此**删除或改造**的决定，
> 至少用两种工具确认，并优先信任 `ripgrep` 结果。
>
> **「零引用」只有在三种证据一致时才成立：包名 + 命名空间 + 短类名，全部 0 命中。**

## 三、升级步骤与执行顺序

### 3.1 总体路线（8 阶段）

```
P0 盘点评估 ──► P1 副本与依赖 ──► P2 配置体系 ──► P3 兼容层重建
                                                      │
                                                      ▼
P7 灰度上线 ◄── P6 门禁与安全 ◄── P5 全站回归 ◄── P4 业务代码机械改造
      │
      ▼
P8 回滚预案（P1 阶段就要备好，不是最后才想）
```

**为什么是这个顺序**（每一步都在为下一步提供"可验证的状态"）：

| 阶段     | 若跳过会怎样                     |
| ------ | -------------------------- |
| P0 盘点  | 工作量估错 2~3 倍；评估报告里一半结论是错的   |
| P1 副本  | 原项目被污染，回滚成本从「秒级」变「天级」      |
| P2 配置  | 后续所有功能验证都在错误配置下跑，结论全废      |
| P3 兼容层 | 252 个控制器逐个改，改到一半发现方向错了     |
| P5 回归  | 只能靠"点点看"，漏掉的分支会在生产上暴露      |
| P6 门禁  | 代码合格但部署不合格（日志可下载、debug 未关） |

### 3.2 阶段详解

#### P0 盘点评估（0.5 天）

| 动作                                                   | 产出        |
| ---------------------------------------------------- | --------- |
| 统计代码规模、控制器/模板/模型数、依赖清单                               | 规模基线      |
| 逐项验证「TP8 是否真的移除了 X」（查新版 vendor 源码，不查博客）              | 差异清单（真实版） |
| 盘点隐性依赖：`config()` 裸键、`select()` 结果、控制器互调、`Cache::rm` | 改造清单 + 估算 |
| 确认改造约束：原地改 vs 副本改                                    | 决策记录      |

**通过标准**：能回答「要改多少处、哪些是脚本能做的、哪些要人判断」。

#### P1 副本与依赖（0.5 天）

```bash
rsync -a --exclude='.git' --exclude='runtime' legacy-app/ tp8-app/
cp composer.json composer.lock.tp51; cp -r vendor vendor.tp51    # 留快照
cd tp8-app && composer require topthink/framework:^8.1 \
  topthink/think-orm topthink/think-multi-app topthink/think-template \
  topthink/think-validate
```

| 要点               | 说明                                                                         |
| ---------------- | -------------------------------------------------------------------------- |
| 保留旧依赖快照          | `vendor.tp51/` + `thinkphp.tp51/`（40MB）：重建兼容层时的**唯一权威依据**                  |
| 旧框架源码别删          | 本案例 `think\Controller`、`Jump`、`Where`、Session 驱动全部照抄 TP5.1 源码重建，比猜实现快 10 倍 |
| `--no-dev` 在预发才用 | 开发期需要 `composer check-platform-reqs` 等工具                                   |

#### P2 配置体系（0.5 天）——**最容易返工的一步**

| 必做项                                        | 原因                                                   |
| ------------------------------------------ | ---------------------------------------------------- |
| 数据库改 `default + connections`               | think-orm 4.x 不收扁平单连接，否则 `Undefined db config:mysql` |
| 多库（`old_db`/`new_db`）迁入 `connections`      | 业务 `Db::connect('old_db')` 调用点才能零改动                  |
| Session 改 `type=cache` + `store=redis`     | TP8 无独立 Redis session 驱动，复用 cache store              |
| 模板 `type='think\Template'`                 | 写 `'Think'` 报 `Driver [Think] not supported`         |
| 模板 `cache_path` **必须显式配**                  | **不配会按进程 CWD 落盘**，FPM 下可能落到 `public/`（明文编译产物可被下载）    |
| 中间件改 `alias` 形式                            | TP8 移除 `default_namespace`，别名大小写敏感                   |
| 多环境目录：`Env::get('CONFIG_PATH') ?: __DIR__` | 原实现依赖外部注入，CLI 直接 Fatal                               |

> **隐性回归警告**：TP5.1 有大量「框架在构造函数里替你补默认值」的配置项，TP8 拆包后默认值变空。  
> **凡是原项目 `config/*.php` 里没显式写的项，都要按"默认值可能已变"重新核一遍**。  
> 本案例唯一不报错、只悄悄改行为的 bug 就来自这里（`cache_path`）。

#### P3 兼容层重建（1 天）

TP8 拆掉的 6 个基础设施，本案例全部**重建而非改写业务**：

| 缺失物                                                                              | 重建方式                                                                                                            | 影响面                   |
| -------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------- | --------------------- |
| `think\Controller`                                                               | 继承 TP8 `BaseController`，照 TP5.1 源码补 `assign/success/error/result/redirect/fetch/display/filter/engine/validate` | 252 控制器全部依赖           |
| `think\response\Jump` + `dispatch_jump.tpl`                                      | 从 TP5.1 源码复制 + 适配 `Response::create`                                                                            | 1,063 处 success/error |
| 全局类别名 `Env/Config/Cache/Session/Cookie/Request/App/Route/Url/View/Lang/Db/Model` | `app/compat.php` 里 `class_alias`                                                                                | 全项目                   |
| `controller()` 助手                                                                | 自建函数（14 文件跨控制器调用依赖）                                                                                             | 63 处 module() 同源      |
| 视图驱动（模板路径解析）                                                                     | 新建 `app/common/view/driver/Think.php`                                                                           | 222 模板                |
| Session 托管                                                                       | 注册 `SessionInit` 中间件 + 入口 `$http->end()`                                                                        | 全站登录                  |

**一个必须注意的坑**：不要注册全局 `Log` 别名。  
阿里云日志 SDK 在全局命名空间声明了 `class Log`，注册别名会触发 `Cannot redeclare`。

#### P4 业务代码机械改造（0.5 天）

按 2.2 的顺序：**先全量替换（脚本）→ 再语法扫描 → 再类加载验证**。  
每一类脚本都要先 `--dry-run` 看 diff，再执行。

#### P5 全站回归（1 天）：见 7.3

#### P6 门禁与安全（0.5 天）：见 6.2

#### P7 灰度 / P8 回滚：见 7.4、7.5

### 3.3 执行顺序上的三条铁律

1. **每一阶段结束时必须有一个可重跑的验证命令**（脚本/清单），否则不许进下一阶段。
2. **兼容层先于业务改造**：兼容层把 1,063 处 `success/error`、252 个控制器一次兜住；先改业务等于把「框架问题」和「改动引入的问题」混在一起。
3. **回滚方案在 P1 就要确定**：本案例的零成本回滚完全来自「独立副本 + 独立 vendor + 独立 FPM 池」。

## 四、关键技术决策及原因

### 4.1 决策总表

| #  | 决策       | 选择的方案                        | 备选                                    | 原因                                                                 | 代价                            |
| -- | -------- | ---------------------------- | ------------------------------------- | ------------------------------------------------------------------ | ----------------------------- |
| D1 | 改造载体     | **复制副本独立改造**                 | 原地升级 + git 分支                         | 原项目零改动 = 回滚秒级                                                      | 双份磁盘；需同步配置                    |
| D2 | 兼容策略     | **重建 TP5.1 基础设施**            | 逐一改写 252 控制器                          | 1,063 处 success/error，改写量是重建的 50 倍                                 | 兼容层自身有 bug 风险（见 D6）           |
| D3 | 类型差异收口   | **在缓存驱动层归一化**                | 在每个 `setRedis()` 调用点加 `toArray()`     | 调用点分散（含 20+ 处 `Cache::set`），漏一处就 500                               | 隐式行为，需注释说明                    |
| D4 | PHP 8 容错 | **按消息特征精确降级**                | `error_reporting(E_ALL & ~E_WARNING)` | 全局关 warning 会吞掉真实故障（除零、文件读不到）                                      | 需维护消息特征列表                     |
| D5 | int 时间字段 | **动态获取器 `withFieldAttr` 短路** | `setOption('dateFormat', false)`      | 全局关 dateFormat 会让 **datetime 列**的类型转换器拿到字符串 → `format() on string` | 需按字段名枚举                       |
| D6 | 回归方式     | **源码反射扫描 + 并发打靶**            | 爬虫 / 人工点菜单                            | 无测试资产且权限表不全；爬虫发现不了未链接入口                                            | 需处理登录态与写操作安全                  |
| D7 | 登录态      | **直接把真实会话写进 Redis**          | 自动化走 CAS 流程                           | CAS 是外部系统、有图形/短信环节，不可自动                                            | 依赖 session 存储格式（易变）           |
| D8 | 环境切换     | **保持 `APP_ENV` 机制，但逐项核对**    | 删掉多环境目录、只留一套                          | 生产切换需要；删了丢失能力                                                      | `APP_ENV` 会顺带改 6 处业务语义（见 6.2） |

### 4.2 D2 展开：为什么"重建"优于"改写"

| 维度   | 重建兼容层                | 逐点改写                                     |
| ---- | -------------------- | ---------------------------------------- |
| 改动量  | 9 个新文件               | 1,063 处 success/error + 252 控制器 + 222 模板 |
| 一致性  | 行为与 TP5.1 完全一致（照源码抄） | 每处改写都可能引入细微差异                            |
| 可回退  | 删掉别名即可               | 无法回退                                     |
| 长期债  | 有（兼容层是技术债）           | 无                                        |
| 适用前提 | 依赖深、业务多、无测试          | 依赖浅、代码少、有测试                              |

> **判断标准**：`success/error` 调用数 > 200 或 控制器数 > 50 → 选重建。  
> 反之改写更干净。**别教条**：小项目重建兼容层是负收益。

### 4.3 D3 展开：收口为什么必须在驱动层

本案例写缓存有**两条路径**，业务代码里混用：

```
路径A: setRedis() 全局函数        → Cache::store('redis')->set()
路径B: Cache::set() 直接调用      → 单文件 20+ 处
```

只在业务调用点加 `->toArray()` 会漏掉路径 B。在 `think\cache\driver\{Redis,File}::set()` 前统一归一化，两条路径自动覆盖。

**但同一个坑还有第二面**：只修写入端不够。  
`getData()` 命中缓存返回 `array`、未命中返回 `Collection`，调用方写死 `->toArray()` → 命中缓存时仍 500。  
**读写两端类型必须一致**（统一 `Collection::make()`）。这是本案例第一轮修复后仍有 500 的直接原因。

### 4.4 D4 展开：降级的边界怎么划

```php
// 只降级这 5 类「PHP 8 提级」消息，其余照常抛异常
Undefined variable / Undefined array key /
Trying to access array offset on null /
Attempt to read property on null /
Automatic conversion of false to array
```

- 命中 → 写日志（前缀 `[TP8][php8-upgraded-notice]`）后 `return true`，取值仍是 `null`，脚本继续。
- 未命中 → 交给框架抛异常，**真 bug 不被掩盖**。
- 日志前缀的价值：把「静默容错」变成「可收集的待办清单」，逐步补 `??` 后收紧匹配范围。


### 4.5 D6 展开：为什么不用爬虫

| 维度 | 爬虫 | 源码反射扫描 |
|---|---|---|
| 覆盖 | 只能发现「有链接的」页面 | 全部 public 方法 + 路由规则 |
| 参数 | 无法构造 | 能按签名分类（必填参数/无参） |
| 写操作 | 无法识别，可能改数据 | 可按方法名 + 方法体双重识别 |
| 稳定性 | 受前端渲染影响 | 纯静态，可复现 |

**但源码扫描有个致命前提**：必须能准确区分「只读」和「写操作」。
本案例第一版只看方法名，把一个方法体里有 `insertAll()` 的接口当只读跑了，**差点污染测试库**。
→ 必须加「方法体正则检测」，并对一次性脚本类控制器（`Demo`/`AjaxDemo`）整体排除。

## 五、遇到的问题与解决方案

### 5.1 核心心智模型：升级断层分七类

把遇到的所有问题归到这 7 类，下次遇到新问题先归类，再按对应策略查：

| 类 | 名称 | 特征 | 识别方法 | 应对策略 |
|---|---|---|---|---|
| **F1** | 配置语义断层 | 键名对了，值读不到 | `config('x')` 返回 `[]` | 全量改 `config('group.x')` |
| **F2** | API 语义漂移（同名不同义） | 方法还在，行为变了 | 比对签名/返回值/默认值 | 逐 API 核对，不凭记忆 |
| **F3** | 默认值蒸发 | 不报错，产物落点变了 | 对「没显式配的项」逐项核 | 全部显式配置 |
| **F4** | 类型契约变化 | 运行时类型错误 | 报错栈指向 `TypeError` | 类型适配层 / 调用点显式转换 |
| **F5** | 容错等级提升 | 原来静默，现在 500 | PHP 8 提级提示 | 精确降级 + 逐步修代码 |
| **F6** | 基础设施拆除 | 类/方法/驱动不存在 | `Class not found` / `Call to undefined` | 重建兼容层 |
| **F7** | 部署耦合暴露 | 换环境才暴露 | 只在 FPM/生产配置下复现 | 环境等价性验证 |

### 5.2 问题全表（按类归档，含定位方法与解法）

#### F1 配置语义断层：影响最大、最隐蔽

| 现象 | 根因 | 定位 | 解法 |
|---|---|---|---|
| CAS 登录死循环；第三方接口数据为空；白名单恒空 | TP5.1 把 `config/` 下所有文件顶层键**合并到一层**；TP8 **按文件名分组** | `config('x')` 返回 `[]` 而 `config('app.x')` 有值 | 35 处 + 模板 5 处改分组键；新增代码严禁裸键 |

> `Config::get()` 对不含点的名字按「一级分组」处理 —— 这是整次升级**唯一能让核心链路完全不可用**的差异，也是最难静态发现的（不报错，只是返回空）。

#### F2 API 语义漂移：TP8 保留了名字，改了含义

| API | TP5.1 | TP8 | 踩法 |
|---|---|---|---|
| `Request::action($convert)` | `$convert=true` → 原始大小写 | **反转**：`true` → 全小写 | 模板名推导错 → `模板文件不存在` |
| `Cache::get()` 未命中 | `false` | **`null`** | 36 处 `if (!$x)` 判断语义变了 |
| `select()` 返回 | `array` | **`Collection`** | 241 处 `array_column()` 崩 |
| `Cache::rm()` | 存在 | **改名 `delete()`，无别名** | `__call` 转发给 phpredis → `TypeError` |
| `think\Controller::__construct()` | 无参 | **`App $app` 必填** | 控制器互调全部 `ArgumentCountError` |
| `Route::group($name, [数组])` | 支持 | **静默不注册**（无报错） | 规则变空壳 → 404/403 |
| 控制器 `return $array / false` | 自动转 JSON / 空响应 | **抛 `variable type error`** | 11 个接口 500 |
| `paginate()` 读 `config('paginate')` | 读整组 | **不再读**，`var_page` 写死 `page` | 自定义分页参数失效 |

**通用做法**：对每个「看起来还能用」的 API，逐一比对 `vendor.tp51` 与 `vendor` 里的签名和返回值，**不要信 TP5.1 的记忆**。

#### F3 默认值蒸发

| 现象 | 根因 | 解法 |
|---|---|---|
| 项目根目录出现 md5 命名的 `.php` 编译文件；FPM 下可能落到 `public/` | TP5.1 `Template::__construct()` 强制补 `cache_path = runtime/temp/`；`think-template` 3.x 默认 `''`，按 CWD 落盘 | `config/view.php` 显式配 `cache_path` |

**复核清单**（本案例逐项实测过，除 `cache_path` 外均已对齐）：
`log.path` / `log.level` / `paginate.type` / `paginate.list_rows` / `paginate.var_page` /
`cookie.secure` / `cookie.expire` / `session.name`。
（其中 `paginate.var_page` 是唯一**语义收窄**项：TP8 的 `paginate()` 不再读 `config('paginate')` 整组，`var_page` 写死 `page`。）

#### F4 类型契约变化

| 现象 | 根因 | 解法 |
|---|---|---|
| `array_column(): Argument #1 must be of type array, Collection given` | `select()` 返回 Collection（`array_*` 只认真 array） | 121 处补 `->toArray()`；`foreach`/`count()`/`$x[0]` 不受影响 |
| **`Serialization of 'Closure' is not allowed`** | TP8 Model 内部持闭包（事件/场景/`_maker`），**不可序列化**；TP5.1 可序列化 | 缓存驱动层归一化（D3）；建议业务侧仍显式 `->toArray()` |
| `Call to a member function format() on string` | 为保住 int 时间字段而 `setOption('dateFormat', false)`，导致 **datetime 列**类型转换器拿到未转换字符串 | 改用 `withFieldAttr` 动态获取器单点短路（D5） |
| `Too few arguments to BaseController::__construct()` | 控制器从「无参普通类」变成「容器托管对象」 | 18 处补 `app()`；长期应下沉到 service |
| `variable type error: array/boolean` | 响应构造不再宽容 | 全局中间件兜底：`$response::class === Html::class` 时按类型转 JSON / 字符串 |

> **中间件判型必须用 `::class ===`**，不能用 `instanceof`：`View extends Response`、`app\response\Jump extends Response` 都会被误伤。

#### F5 容错等级提升

| 现象 | PHP 7.4 | PHP 8.x |
|---|---|---|
| `Undefined variable` / `Undefined array key` | E_NOTICE（静默） | **E_WARNING → TP8 抛异常** |
| `Trying to access array offset on null` | E_NOTICE | **E_WARNING** |
| `Passing null to parameter` | 无 | E_DEPRECATED |
| `Automatic conversion of false to array` | 无 | E_DEPRECATED |

TP8 的 `think\initializer\Error::init()` **无条件** `error_reporting(E_ALL)`，命中即 `throw ErrorException`。
→ 「数组键没判空」从「静默继续」变成「整页 500」。解法见 D4。

#### F6 基础设施拆除

| 缺失 | 现象 | 解法 |
|---|---|---|
| `think\Controller` | 所有控制器 Fatal | `BaseController` 重建 + `class_alias` |
| `think\response\Jump` + 模板 | 1,063 处 success/error 崩 | 三件套重建（trait + response + tpl） |
| 视图驱动层 | `模板文件不存在:public/default.html` | 自建 `view/driver/Think.php` 补路径解析 |
| Session 自动托管 | 反复提示无权限、反复重登 | 注册 `SessionInit` + 入口 `$http->end($response)` |
| `old_db`/`new_db` 扁平配置 | `Undefined db config` | 迁入 `connections` |
| `Db` 门面 | 81 文件 | `class_alias('think\facade\Db','Db')`（`think\Db` **无** `__callStatic`） |

**Session 那个坑尤其阴**：缺陷 1（未注册中间件）+ 缺陷 2（入口缺 `end()`）叠加后，
**同一次请求内 session 读写完全正常**，只有跨请求才丢 —— 表面像"权限配置不对"，实际是会话没保存。

#### F7 部署耦合暴露

| 现象 | 根因 | 解法 |
|---|---|---|
| 换机器后没报错，跑到导出才崩 | `composer.json` 漏声明 `redis/xml/dom/simplexml/xmlwriter/fileinfo/bcmath/pdo_mysql` | 补齐声明，让 `check-platform-reqs` 有效 |
| 日志写飞 / 导出目录不存在 | 相对路径落盘（`../runtime/export`、`./SYS_LOG/`、`./allLogs/`、`./api_log/`）依赖进程 CWD | 用 `dirname(__DIR__)` 或 `runtime_path()` 锚定绝对路径 |
| **日志目录可匿名下载，含学生姓名 + 手机号 + 身份证** | 同上：相对路径在 FPM 下 cwd = `public/`，日志落进 web 根 | 三层：① 路径锚定 `runtime/log/`（治本）② 删历史文件 ③ nginx `^~ { return 404; }`（纵深防御） |
| 判断「是否 CWD 依赖」没有直接线索 | —— | **识别方法**：同一个相对路径在 **web 触发** 与 **CLI 触发** 下出现在两个不同位置（本案 `public/SYS_LOG` 8.9M vs 项目根 `SYS_LOG` 20K），即为 CWD 依赖的铁证 |
| 8.3 跑得好、8.4 未知 | vhost 实际 PHP 版本与验证基准不一致 | 用内置 server 或独立 FPM 池做**同批链接跨运行时对比** |

### 5.3 三个"假象"陷阱（本案例全部踩过）

| 陷阱 | 表现 | 正确做法 |
|---|---|---|
| **未登录态验证** | 所有受保护路径统一 302 到 CAS，看起来"一致地正常" | **鉴权链路必须用真实会话验证**；权限判定错误只在登录态现形 |
| **`WARN_EMPTY` 当无害** | 200 空响应，其实是方法开头 `checkRepeat()` 命中防重锁 `die`，把 SQL 错误盖住了；另一个案例：某二维码接口因 `content` 为空提前 `return ''`，把「依赖包已删除」的致命错误一路盖到用户点击才暴露 | 区分「业务本无输出 / 参数缺失走了早退分支 / 被前置逻辑提前 return」三种情况，**逐个抽查，不能整类放过** |
| **无参回归测不出「有参才执行」的缺陷** | 参数从 `Request::get('k','')` 取而非方法签名，静态扫描得 `params_required=0` → 归入可自动执行；无参调用只走早退分支 → `WARN_EMPTY` | 对「签名无参但方法体含 `Request::get/post('k')`」的入口单列清单，逐个填占位值验证 |
| **扫描结果异常偏高/偏低** | 静态扫描报 134 处告警，全是假的（正则分组不存在被判成 `!== ''`） | 先怀疑解析器本身，用「已知正确样本」校准 |

### 5.4 排查方法论：先分层，再定位

```
500 了
 ├─ 看报错栈的 file 归属
 │   ├─ vendor/  → F2/F3/F6（框架语义或缺失）→ 查 TP5.1 源码对比
 │   └─ app/     → F4/F5（类型或容错）→ 查该行变量来源
 ├─ 是否只在"特定数据/特定 URL"上炸？
 │   └─ 是 → F2（同名不同义）概率最高
 ├─ 是否只在"跨请求"时异常？
 │   └─ 是 → Session / Cookie / 缓存链路
 ├─ 是否只在"部署后"异常？
 │   └─ 是 → F7（扩展/路径/权限/版本）
 └─ 是否不报错但行为不对？
     └─ F1（配置分组）/ F3（默认值蒸发）
```

## 六、风险与注意事项

### 6.1 技术风险（精简版，按处置优先级排序）

| 优先级 | 风险 | 影响 | 处置 |
|---|---|---|---|
| P0 | 配置分组语义断层 | 核心链路静默失效 | 全量改分组键 + 新增代码评审卡点 |
| P0 | Session 未托管 | 无法登录 | 中间件 + 入口 `end()` + 清历史会话 |
| P0 | **`public/` 下日志目录可匿名下载** | 个人信息泄露 | nginx `deny` + 移出 web 根 |
| P0 | `APP_DEBUG=1` 上生产 | 泄露绝对路径与堆栈（实测 139KB vs 6.8KB） | 环境门禁强制检查 |
| P1 | Model/Collection 不可序列化 | 所有「查询结果进缓存」的地方 500 | 驱动层归一化 |
| P1 | 控制器返回值不再宽容 | API 批量 500 | 中间件兜底 |
| P1 | `select()` 返回 Collection | `array_*` 崩 | 脚本补 `toArray()` |
| P1 | PHP 8 容错等级提升 | 大面积 500 | 精确降级 + 逐步修 |
| P2 | CAS 真实登录未验证 | 上线后无人能登录 | **必须人工登录一次**，不能用假 code 判定 |
| P2 | 第三方 SDK 不兼容 8.4（阿里云日志 0.6.8 隐式可空） | debug 下中断 | 推动升级 / `APP_DEBUG=0` 规避 |
| P3 | 临时归档 40MB | 磁盘 | 稳定后删除 |

### 6.2 上线风险：环境切换的隐藏耦合

**`APP_ENV=production` 不只切配置文件，还会切业务语义**（本项目实测 6 处）：

| 位置 | 切换后行为 |
|---|---|
| 钱包接口 | → 真实资金接口 |
| 短信接口 | → 真实发送 |
| 报表接口 | → 真实接口 |
| 业务分界常量（批次/届别编号等） | 硬编码分界值被改动（**可能让历史数据判错届别**） |
| CAS 地址 | → 生产 CAS |

**还有两个反直觉的实测结论**：

1. `APP_ENV=production` **不会自动关 debug**（`app_debug` 直接读 `APP_DEBUG`）。
2. **也不会自动切数据库**（`production/database.php` 全部从 `Env::get(config_database.*)` 读）。

→ 环境切换必须**逐项核对**，不能假设「切了环境就对了」。

### 6.3 十一条红线（Do Not）

1. **不要在 `APP_DEBUG=1` 下上线**（泄露源码路径、SQL、堆栈）。
2. **不要用假 code 换 token 来判断 CAS 是否可用**（无效 code 未做异常处理，生产环境同样 500）。
3. **不要只修写入端不修读取端**（缓存命中/未命中类型必须一致）。
4. **不要用 `instanceof` 判断响应类型**（继承链会误伤，用 `::class ===`）。
5. **不要全局关 warning / 不要把 `dateFormat` 设成 `false`**（前者吞真故障，后者毁 datetime 列）。
6. **不要用方法名判断写操作**（必须看方法体）。
7. **不要相信「评估报告说必须改」**（先 grep 真实引用数）。
8. **不要删除旧依赖快照就开工**（`vendor.tp51` 是重建兼容层的唯一依据）。
9. **不要在配置体系修好前批量改业务代码**（改了无法验证，等于白改）。
10. **不要把「200 空响应」一律当正常**（可能是前置逻辑 `die` 掩盖了真实错误）。
11. **不要先删历史日志、后改代码**（删完的瞬间 web 请求又会长出来）。敏感文件处置的正确顺序是
    **① 改代码锚定路径 → ② 删历史文件 → ③ 加 nginx 规则**；顺序颠倒会做两遍。

## 七、验证与回滚方式

### 7.1 五层验证模型（逐层递进，不可跳层）

| 层 | 验证内容 | 工具 | 通过标准 |
|---|---|---|---|
| V1 静态 | 语法、类加载、函数可用性 | `php -l` 全扫 / 反射加载 / `function_exists` 扫描 | 0 错误 / 0 失败 / 0 缺失 |
| V2 组件 | DB / ORM / Cache / Session / 模板 / Excel / Validate / 助手 | 冒烟脚本（可重复执行） | 14/14 PASS |
| V3 链路 | 路由、鉴权、CAS 跳转、回调 | curl（未登录 + **真实会话**两种） | 状态码符合预期，无 500 |
| V4 业务 | 全站入口 | **自动回归工具**（见 7.3） | 通过率 ≥ 95%，失败项全部定性 |
| V5 环境 | 目标运行时 / 生产配置 | 跨运行时对比 + 门禁清单 | 差异可解释，清单全绿 |

### 7.2 关键量化基线（本案例，可作为你的通过线）

```
V1: 语法 0 错误（app/config/route/vendor 全扫）
    类加载 243/243
    V2: 冒烟 14/14 PASS
    全站回归: 373 条可执行 → 356 通过 (95.4%)，500 仅 3 条且均定性为非缺陷
             三轮复跑（冷缓存/热缓存/一键脚本）判定不一致 0 条
    V5: PHP 8.4 vs 8.3 逐 URL 差异 3 条，均有解释，无 8.4 特有问题
```

> **「判定不一致 0 条」比「通过率 95%」更有价值**：它证明工具本身稳定，不是碰巧这次过了。

### 7.3 全站回归工具的设计（可直接复用）

**核心思路**：把「找链接」和「打链接」分开，中间产物落盘，可单独重跑。

```
discover.php  →  urls.json  →  run.php  →  result.json  →  report.php  →  md + csv
   (反射扫描)                  (并发打靶)                  (根因聚类)
```

| 模块 | 关键设计 | 为什么必须这么做 |
|---|---|---|
| 入口发现 | 反射 `app/*/controller/*.php` 全 public 方法 + 路由文件显式规则 | 权限表不全，爬虫发现不了未链接入口 |
| 分类 | `page` / `ajax` / `route` / `write` / `param` | 只有前三类可安全自动执行 |
| 写操作识别 | 方法名关键词 **+ 方法体正则**（`insert/update/save/execute/destroy`）双检测；`Demo` 类整体排除 | 命名看不出写库的方法真实存在，会污染数据 |
| 登录态 | 直接构造 session 写入 Redis | CAS 是外部系统，无法自动化 |
| 判定 | `PASS` / `FAIL_500` / `FAIL_RUNTIME`（200 但含 PHP 错误）/ `FAIL_404` / `FAIL_AUTH` / `FAIL_NET` / `WARN_EMPTY` | 只看状态码会漏「200 但页面里是异常信息」 |
| 定性 | `nature_of()` 判断「要不要动代码」：缺参数 / 缺表(环境) / 需签名 / 批处理超时 / 待查 | **避免把环境问题当代码缺陷修** |
| 聚类 | 按「表不存在 / 字段不存在 / 对 null 调用 / 参数不足 / 数组当字符串 / Closure 序列化 / 返回值类型 / 模板缺失」 | 支撑「按类别统一修复」而不是逐个打补丁 |

**本案例执行结果**（说明工具的实际价值）：

| 轮次 | 被测 | 通过 | 通过率 | 500 |
|---|---|---|---|---|
| 修复前 | 425 | 361 | 84.9% | **35** |
| 缓存/响应修复后 | 425 | 380 | 89.4% | 6 |
| 补充修复后 | 425 | 383 | 90.1% | 4 |
| 最终（剔除写操作） | 373 | 356 | **95.4%** | **3** |

**按类别修复 6 类，35 → 3**：① Closure 序列化（9 页）② 返回值类型（11 接口）③ 集合当数组（3 接口）④ PHP 8.2 废弃函数（1 页）⑤ 不存在的方法（1 页）⑥ 上传判空（2 接口）。

> **「按类别修」比「逐个修」效率高一个量级**：一轮修完一类，重跑验证，再修下一类。
> 逐个修会让每一轮都要重新确认前面是否回退。

**工具的边界（必须在文档里写明）**：
- 写操作（170 条）与必填参数（388 条）不自动测，只能人工按业务场景验证。
- 批处理接口会超时，需单独对待。
- 测试库缺表不算代码缺陷。

### 7.4 回滚设计（贯穿全程，不是最后才想）

| 层级 | 回滚动作 | 生效时间 | 前置条件 |
|---|---|---|---|
| 流量 | nginx upstream 权重切回原池 | 秒级 | 新旧 FPM 池并存 |
| 代码 | 切回原目录 | 秒级 | **原项目零改动** |
| 依赖 | 新项目独立 vendor，不影响原项目 | — | 副本改造 |
| 数据 | 库结构未改（只改代码） | — | 升级期间禁 DDL |
| 会话 | 清 Redis 会话，用户重登一次 | 分钟级 | 新旧 session 结构不同，必然互不识别 |

**回滚触发阈值**（建议直接沿用）：
`5xx 率 > 0.5%` / `登录成功率下降 > 1%` / `CAS 回调异常` / `核心写操作失败`

### 7.5 灰度观察

```
5% → 20% → 50% → 100%（每档至少观察 30 分钟，覆盖一个业务波峰）
```

必看指标：5xx 率、登录成功率、CAS 回调、DB 写入正确性、导出文件可打开性、缓存命中率。

## 八、可复用的经验与建议

### 8.1 十二条经验（按价值排序）

1. **先造尺子，再量身高。** 0 测试资产的老项目，第一件事是建自动回归工具；否则「改完不知道对不对」会贯穿全程。
2. **兼容层 > 逐点改写。** 依赖深的项目，重建 TP5.1 基础设施（照源码抄）成本远低于改写调用点，且行为更一致。
3. **旧依赖快照是资产，不是垃圾。** `vendor.tp51` + `thinkphp.tp51` 让「新版到底改了什么」有据可查，比查文档快 10 倍。
4. **所有「不报错的差异」最危险。** 配置分组、默认值蒸发、`WARN_EMPTY` 都不报错，却能让核心链路静默失效。
5. **按类别修，不逐个修。** 聚类后一轮修一类，重跑验证，效率高一个量级。
6. **收口在最窄的一层，但要注意「窄」不等于「单端」。** 缓存问题要同时修写入端和读取端，只修一端等于没修。
7. **兼容层的每行「全局覆盖」都要问副作用面。** `dateFormat=false` 只为一个分支短路，却毁了所有 datetime 列。
8. **精确降级 > 全局关闭。** 按消息特征匹配，才能既保住 PHP 7.4 语义，又不掩盖真 bug。
9. **验证必须用真实身份。** 未登录态下所有受保护路径都 302，看起来「一致地正常」，掩盖了权限判定错误。
10. **「假 code / 假数据」不能判定外部依赖是否可用。** 要先确认该接口对无效输入是否做了异常处理。
11. **扫描脚本异常偏高偏低时，先怀疑解析器。** 用已知正确样本校准，别急着照告警改代码。
12. **回滚成本在 P1 阶段就锁定了。** 「副本 + 独立 vendor + 独立 FPM 池」= 秒级回滚，这是整个升级最划算的投资。
13. **删依赖比改代码更危险，因为它看起来最安全。** 「零引用」必须三证据一致（包名 / 命名空间 / 短类名全部 0 命中）+ 两种工具交叉验证；`grep` 大小写和偶发漏搜都会让你误删正在用的能力，而 `WARN_EMPTY` 会帮它藏到用户点击那天。
14. **验收要验到"业务正确"，不是"执行成功"。** 二维码生成返回 200 不等于码可用 —— 必须解码比对内容；导出不报错不等于数据对 —— 必须开文件看单元格。**能"看起来成功"的功能，都要加一层结果校验。**


### 8.2 反模式清单

| 反模式 | 后果 | 正确做法 |
|---|---|---|
| 在配置体系修好前批量改业务代码 | 改动无法验证，白改一轮 | P2 完成并通过验证再进 P4 |
| 只改调用点，不做兼容层 | 改动量爆炸，且容易漏 | 驱动层/基类层收口 |
| 用 `grep -v '//'` 过滤注释来扫调试残留 | 块注释、`#` 注释漏网 | AST 解析或按行首 token 判断 |
| 用 `instanceof` 判响应类型 | 继承链误伤 | `::class ===` |
| 把环境问题（缺表/缺参数）当代码缺陷修 | 越修越乱 | 先定性，再决定是否动代码 |
| 相信评估报告而不 grep 真实引用 | 做了 4 个不需要做的改造 | 先验证引用数，零引用直接删 |
| **按包名小写搜一遍就判定「零引用」并删依赖** | 删掉仍在使用的能力（如二维码），且回归测不出来 | 包名/命名空间/短类名三种搜法 + 双工具交叉，见 2.4.1 |
| 扫描脚本报出大量告警就直接改 | 改错方向 | 先用已知样本校准脚本 |
| 上线前不验证 debug 关闭后的错误页 | 泄露源码路径与堆栈 | 对比 debug 开关下的响应体大小与内容 |

### 8.3 给下一个项目的 30 分钟启动清单

```bash
# 1. 摸清规模
find app -name "*.php" | wc -l; find app -name "*.html" | wc -l

# 2. 摸清隐性依赖（这四项决定工期）
grep -rn "config('[a-z_]*')" app/ | wc -l          # F1 风险面
grep -rn -- "->select()" app/ | wc -l              # F4 风险面
grep -rn "new [A-Z][A-Za-z]*(" app/ | wc -l        # 控制器互调风险面
grep -rn "\->rm(\|Cache::rm" app/ | wc -l          # 已移除 API

# 3. 验证「必须改」的结论（别信报告）
grep -rln "think\\\\Db;" app/ | wc -l
grep -rn "Request::module()" app/ | wc -l

# 4. 备份基准
cp -r vendor vendor.tp51; cp -r thinkphp thinkphp.tp51; cp composer.lock composer.lock.tp51

# 5. 先问三个问题
#    debug 现在是几？ 生产 .env 谁维护？ web 根下有没有日志/备份目录？
```

### 8.4 什么情况下不要升级

| 情况 | 建议 |
|---|---|
| 只为了「用新版」 | 不值得。TP5.1 仍在安全支持期的项目可继续维护 |
| 没有灰度能力 / 不能停机 | 先解决发布能力，否则升级风险不可控 |
| 代码量 < 5 万行且有测试 | 考虑**直接重写核心模块**，而不是迁移历史包袱 |
| 强依赖已停止维护的第三方 SDK | 先解决 SDK，再谈框架 |
| 目标只是 PHP 8 兼容 | 可以先升 PHP 8.2/8.3 + 少量 shim，框架不动，风险低一个量级 |

### D. 版本与术语对照

| 项 | TP5.1 | TP8 |
|---|---|---|
| 应用目录 | `application/` | `app/` |
